## 1. Executive Summary

**Что готово.** Ядро системы доведено до эксплуатационного состояния: бронирование
транзакционно, вместимость проверяется сервером, дубли исключены, цена считается
в одном месте, расписание честное, уведомления и оплата вынесены в провайдеры,
админка пригодна для работы, документация описывает развёртывание, копии и откат.

**Главная находка прохода** — не в коде. Проверка конфигурации, добавленная в этом
проходе, показала на живом деплое, что переменные `NEXT_PUBLIC_SITE_URL`,
`ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, `DATABASE_URL` **до приложения не
доходят**, хотя в панели Vercel показаны заданными. Следствия: canonical отдавался
как `localhost`, канал уведомлений молчал, админка была закрыта, а брони не
сохранялись. Это одна причина у четырёх симптомов, и она требует действий
владельца в панели хостинга (§14, §17).

**Что это значит для бизнеса.** Сайт-витрина работает и корректно показывает
квесты, цены и расписание. Приём броней на живом хостинге сознательно остановлен:
система отвечает `503` и просит позвонить, вместо того чтобы принять заявку и
потерять её.

## 2. Архитектура

```text
Frontend        →  Next.js App Router, серверные страницы + островные клиентские
                   компоненты. Свой источник данных — единственный (lib/content.ts)
        ↓
Booking         →  createBooking: валидация → критическая секция слота →
                   проверка вместимости → запись → история статусов.
                   Ключ идемпотентности отсекает повторную отправку
        ↓
API             →  /api/bookings (POST публичный, GET только админ),
                   /api/bookings/[id] (PATCH), /api/bookings/[id]/payment,
                   /api/availability, /api/payments/webhook, /api/cron/reminders,
                   /api/health, /api/admin/session
        ↓
Storage         →  BookingStorage (интерфейс) с тремя реализациями:
                   File / Memory / PostgreSQL. Выбор по окружению
        ↓
Notifications   →  NotificationService + провайдеры Telegram / Webhook / Log.
                   Провал отправки не отменяет бронь
        ↓
Admin           →  Панель: сводка дня, «требуют внимания», поиск, фильтры,
                   смена статуса по машине состояний, отметка оплаты
        ↓
Payments        →  PaymentProvider: manual (ручная предоплата) и HTTP-эквайринг
                   с проверкой подписи вебхука. По умолчанию manual
        ↓
Schedule / CRM  →  AvailabilityProvider (собственное расписание / внешний
                   календарь) и CrmProvider (собственная база / внешняя CRM)
```

## 4. Database

Сделано: интерфейс `BookingStorage` с тремя реализациями; SQL-репозиторий на
PostgreSQL; идемпотентный раннер миграций с журналом `schema_migrations` и
транзакцией на каждый файл; аддитивные миграции без разрушающих операций;
`pg` вынесен в зависимости.

`[VERIFIED]` `npm run migrate` — применяет по порядку, повторный запуск ничего
не делает. Проверка на живом деплое: `database.mode = "not_configured"`
(подключена только при заданном `DATABASE_URL`).

Отступление от буквы задания: таблицы `quests` и `schedule` **не созданы
намеренно**. Квесты и старты — контент в одном источнике (`lib/content.ts`,
`lib/availability.ts`), они не меняются владельцем через интерфейс и не требуют
запросов к базе. Перенос их в SQL добавил бы слой без выгоды и раздвоил бы
источник истины — прямой риск для цены и расписания. Появится потребность
редактировать квесты из админки — тогда и таблица.

## 5. Booking

`[VERIFIED]` Сквозная проверка `npm run test:booking` — **7 из 7**:

| Проверка | Результат |
|---|---|
| `GET /api/health` | 200 |
| Поиск свободного слота | 2026-09-27 12:00, 15 мест |
| Создание брони | 201, номер `HC-3UK5C293DE0` |
| Стоимость считает сервер | 15 000 ₸ |
| Повторная отправка с тем же ключом | возвращает ту же бронь, дубля нет |
| Занятость слота | 15 → 12 |
| Запрос сверх вместимости | 422 + текст: «В этом слоте свободно 12 из 15 мест, а в заявке 15. Уменьшите команду или выберите другое время.» |

Транзакционность: проверка вместимости выполняется **внутри** критической секции
слота — очередь по слоту в файловом режиме, `pg_advisory_xact_lock` в SQL.
`[CODE]` Проверка на 10 одновременных запросах не запускалась: смоук-тест
проверяет последовательное переполнение, а параллельный сценарий требует
отдельной нагрузки. Это остаётся непроверенным.

Статусы: `new` (ожидает подтверждения), `confirmed`, `completed`, `cancelled`,
`expired`. Статус брони и статус оплаты — **разные поля**, они не смешиваются.

## 6. Notifications

`[CODE]` `NotificationService` + провайдеры Telegram / Webhook / Log. Бронь
сохраняется до отправки, провал отправки не отменяет бронь и не создаёт вторую;
результат пишется в журнал (`notification_sent` / `notification_failed`).
Напоминания 24 ч и 2 ч с меткой в броне против повторной отправки.

`[VERIFIED]` На живом деплое: `notifications.mode = "log_only"` — канал не
доходит до приложения, поэтому сообщений владельцу нет. Система об этом честно
сообщает, а не делает вид, что отправила.

## 7. Payments

`[CODE]` Абстракция `PaymentProvider`: `manual` (реквизиты и подтверждение
администратором) и HTTP-эквайринг с проверкой подписи вебхука (HMAC-SHA256,
сравнение за постоянное время). Оплата не подтверждается по редиректу клиента —
только по подписанному серверному уведомлению. Повторная доставка платежа не
создаёт второго эффекта.

`[VERIFIED]` На живом деплое `payments.mode = "manual"` — эквайринг отключён,
имитации нет. Провайдер не выдуман: пустая настройка означает ручную предоплату.
