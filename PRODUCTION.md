# PRODUCTION — эксплуатация сайта

Документ для того, кто выкладывает сайт и ведёт его после запуска.
Описывает только то, что реально есть в коде: ничего «на будущее».

---

## 1. Быстрый старт

```bash
npm install
npm run build
npm start                 # http://localhost:3000
```

Проверка состояния после запуска:

```bash
curl -s localhost:3000/api/health | jq
```

`/api/health` отвечает кодом **200**, пока хранилище работает, и **503**, если нет.
Секретов в ответе нет — только состав конфигурации.

---

## 2. Переменные окружения

Полный список с пояснениями — в [`.env.example`](.env.example).

**Обязательно в продакшене:**

| Переменная | Зачем |
|---|---|
| `NEXT_PUBLIC_SITE_URL` | canonical, sitemap, Open Graph, ссылки «поделиться» |
| `ADMIN_PASSWORD` | вход в `/admin`; без неё панель отключена |
| `ADMIN_SESSION_SECRET` | подпись cookie админ-сессии |

В продакшене ни одна функция не имеет пароля по умолчанию. Это сделано
намеренно: панель, доступная «пока пароль не задан», — это открытая панель.
Единственное исключение — режим разработки (`NODE_ENV=development`), где
действует пароль `horror-clinic`, чтобы `npm run dev` не требовал настройки.
Поэтому dev-сборку нельзя выставлять в интернет или на стенд с внешним
доступом: любое окружение, кроме явного development, закрыто.

**Никогда не задавать в продакшене:**

| Переменная | Почему |
|---|---|
| `ALLOW_TEST_ENDPOINTS` | открывает сброс лимита частоты для автотестов |
| `DEMO_AVAILABILITY` | включает **выдуманную** занятость слотов (только для показа) |

## 3. Хранилище броней

Сейчас поддерживаются три реализации, переключаемые окружением:

| Режим | Когда используется | Где данные |
|---|---|---|
| Файловое | по умолчанию | `.data/bookings.json` |
| PostgreSQL | задан `DATABASE_URL` | таблица `bookings` |
| В памяти | тесты | процесс |

### Переход на PostgreSQL

```bash
npm i pg
export DATABASE_URL=postgres://user:pass@host:5432/quest
npm run migrate
```

`npm run migrate` применяет файлы из `db/migrations` строго по порядку имён,
каждый — в отдельной транзакции, и записывает применённое в `schema_migrations`.
Повторный запуск ничего не делает. Если упала середина файла, он не применяется
целиком — база не остаётся в половинчатом состоянии.

### Однопоточность и гонки

Вместимость слота проверяется **внутри критической секции**, привязанной к слоту:

* в файловом режиме — очередь промисов по ключу слота (разные слоты не блокируют друг друга);
* в PostgreSQL — `pg_advisory_xact_lock` внутри транзакции.

Поэтому два одновременных запроса на последнее место не могут оба пройти.
Проверка вместимости на клиенте — только подсказка, решает сервер.

## 3.1. Развёртывание на Vercel (serverless) — важное ограничение

**Проверено на живом деплое:** файловое хранилище на Vercel брони не сохраняет.
Запись в каталог приложения не переживает перезапуск инстанса, и при этом
`POST /api/bookings` отвечает `201`, а клиент видит экран «вы записаны».
Заявка теряется — площадка о ней не узнаёт.

Поэтому система сама останавливает продажу. Перед созданием брони проверяется
долговечность хранилища, и при отказе API возвращает:

```
503  {"ok":false,"retryable":false,
      "message":"Онлайн-бронирование временно недоступно.
                 Позвоните или напишите нам в WhatsApp — забронируем вручную за минуту."}
```

В журнал пишется `booking_rejected_storage_not_durable` уровнем `error`.
`/api/health` в этом состоянии отдаёт `ok: false`, `storage.writable: false`
и предупреждение с указанием, что именно задать.

**Чтобы бронирование заработало на Vercel:**

1. Создайте базу: Vercel Postgres, Neon или любой managed PostgreSQL.
2. Добавьте `DATABASE_URL` в Environment Variables проекта Vercel.
3. Примените схему: `npm run migrate` (локально, с тем же `DATABASE_URL`).
4. Перезапустите деплой и проверьте:
   `curl -s https://<домен>/api/health` → должно быть
   `database.mode: "connected"`, `storage.mode: "sql"`, `storage.writable: true`.

Драйвер `pg` уже в зависимостях — устанавливать вручную ничего не нужно.
На обычном сервере (VPS, Docker) ограничение не действует: там файловое
хранилище работает, `storage.writable: true`.

## 4. Планировщик

`/api/cron/reminders` — проход напоминаний и истечение броней.

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://example.kz/api/cron/reminders
```

* Требует `CRON_SECRET`. Без него эндпоинт доступен только администратору.
* Рекомендуемый интервал — каждые 15–30 минут.
* Напоминания 24 ч и 2 ч от начала игры; отправка помечается в броне
  (`remindersSent`), поэтому повторный запуск не отправит одно и то же дважды.
* Брони, которые не подтвердили до начала игры, переводятся в статус «истекла».

**Важно:** напоминания уходят только в те каналы, которые настроены
(Telegram / вебхук). Если ничего не настроено, проход фиксирует, кому напомнить,
но никому не пишет и не делает вид, что написал.

## 5. Оплата

Схема по умолчанию — **ручная предоплата**:

1. клиент оставляет заявку, она сохраняется со статусом «ожидает подтверждения»;
2. администратор пишет в WhatsApp и присылает реквизиты;
3. администратор отмечает «предоплата получена» в админке — только после этого
   бронь переходит в «подтверждена».

Онлайн-эквайринг подключается переменными `PAYMENT_API_URL`, `PAYMENT_API_KEY`,
`PAYMENT_WEBHOOK_SECRET`. Правила, которые соблюдает вебхук
(`POST /api/payments/webhook`):

* подпись тела проверяется (HMAC-SHA256, сравнение за постоянное время); без
  корректной подписи запрос отклоняется;
* редирект клиента на «страницу успеха» доказательством оплаты не считается —
  оплату подтверждает только подписанный серверный вебхук;
* повторная доставка того же платежа не создаёт второго эффекта: событие
  сопоставляется с бронью по номеру платежа;
* в логах нет тела запроса с персональными данными.

## 6. Внешняя система учёта (CRM)

По умолчанию система учёта — собственная база, отдельная CRM не нужна.
Если заведение ведёт учёт вовне, задайте `CRM_API_URL` и `CRM_API_TOKEN`:
бронь выгружается туда после сохранения.

Если выгрузка не удалась, это **не теряется и не скрывается**:

* результат пишется в бронь (`crmSync`), администратор видит пометку
  «CRM: не выгружено»;
* бронь остаётся в статусе «ожидает подтверждения» — то есть система не
  утверждает, что всё согласовано, пока это не подтвердил человек.

## 7. Расписание и занятость

Источник истины по занятости — **реальные брони**. Слот свободен, пока в нём
есть места: площадка работает по фиксированной сетке стартов, все старты
доступны, пока их не заняли.

* `DEMO_AVAILABILITY=1` добавляет **выдуманную** занятость. Это инструмент показа,
  а не функция продукта. На рабочем сайте переменная должна быть снята.
* Внешний календарь подключается через `AVAILABILITY_API_URL`. Если он
  недоступен, API отвечает `503` и честным текстом «расписание недоступно» —
  вместо того чтобы показать устаревшие данные как актуальные.

## 8. Подготовка к показу владельцу

```bash
# 1. Убрать тестовые брони, чтобы в админке не было чужих записей
#    (файл в .gitignore, данные никуда не уходят — просто переместите его)
move .data\bookings.json %TEMP%\bookings-archive.json

# 2. Собрать и запустить
npm run build
npm start
```

Проверьте перед показом: главная открывается, календарь отдаёт слоты,
заявка создаётся, админка пустая и чистая, `/api/health` отвечает 200.

## 9. Проверки

```bash
npm test              # типы + линтер
npm run verify        # типы + линтер + production-сборка
npm run test:smoke    # сквозной смоук API (нужен запущенный сервер)
```

Смоук-тест требует запущенного сервера с открытым служебным сбросом лимитов:

```bash
# Windows PowerShell
$env:ALLOW_TEST_ENDPOINTS=1; npm start
# в другом окне
npm run test:smoke
```

Тест проверяет 46 утверждений: доступность слотов, создание брони, цену,
защиту от дубля, валидацию, отказ по прошедшей дате, **переполнение слота**,
закрытость админки, вход с чужого домена, лимит частоты, заголовки безопасности
и наличие структурированных данных.

Скрипт `scripts/scan-hidden-chars.mjs` ищет невидимые символы переноса
(soft hyphen, zero-width space) в исходниках — они незаметно рвут слова
в интерфейсе. Запуск: `node scripts/scan-hidden-chars.mjs`.

## 10. Что сознательно не сделано

Честный список, чтобы не было ложных ожиданий:

* **онлайн-эквайринг не подключён** — есть интерфейс провайдера и проверка
  вебхука, но конкретная платёжная система не выбрана;
* **SMS и e-mail не отправляются** — нужен провайдер; клиент получает
  подтверждение на экране, файл в календарь и ссылку в WhatsApp;
* **внешняя CRM не подключена** — есть адаптер и обработка ошибок выгрузки;
* **e2e-тесты в браузере отсутствуют** — сквозные проверки идут на уровне API
  (смоук-тест); для UI-регрессий нужен Playwright;
* **напоминания клиенту** требуют настроенного канала; без него планировщик
  только фиксирует список.
