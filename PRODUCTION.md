# PRODUCTION — эксплуатация сайта

Документ для того, кто выкладывает сайт и ведёт его после запуска.
Описывает только то, что реально есть в коде: ничего «на будущее».

---

## 1. Быстрый старт

```bash
npm install
npm run build
npm start                 # http://localhost:3000
```

Проверка состояния после запуска:

```bash
curl -s localhost:3000/api/health | jq
```

`/api/health` отвечает кодом **200**, пока хранилище работает, и **503**, если нет.
Секретов в ответе нет — только состав конфигурации.

---

## 2. Переменные окружения

Полный список с пояснениями — в [`.env.example`](.env.example).

**Обязательно в продакшене:**

| Переменная | Зачем |
|---|---|
| `NEXT_PUBLIC_SITE_URL` | canonical, sitemap, Open Graph, ссылки «поделиться» |
| `DATABASE_URL` | хранение броней; на serverless без неё онлайн-бронирование честно отключается |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | уведомление владельцу о каждой новой заявке |

Панели администратора у сайта нет: заявка уходит в Telegram/вебхук, а
подтверждает её человек в переписке. Если уведомления не настроены, заявка
всё равно сохраняется, но владелец узнаёт о ней не сразу — это единственный
режим, который стоит закрыть до запуска рекламы.
Единственное исключение — режим разработки (`NODE_ENV=development`), где
действует пароль `horror-clinic`, чтобы `npm run dev` не требовал настройки.
Поэтому dev-сборку нельзя выставлять в интернет или на стенд с внешним
доступом: любое окружение, кроме явного development, закрыто.

**Никогда не задавать в продакшене:**

| Переменная | Почему |
|---|---|
| `ALLOW_TEST_ENDPOINTS` | открывает сброс лимита частоты для автотестов |
| `DEMO_AVAILABILITY` | включает **выдуманную** занятость слотов (только для показа) |

## 3. Хранилище броней

Сейчас поддерживаются три реализации, переключаемые окружением:

| Режим | Когда используется | Где данные |
|---|---|---|
| Файловое | по умолчанию | `.data/bookings.json` |
| PostgreSQL | задан `DATABASE_URL` | таблица `bookings` |
| В памяти | тесты | процесс |

### Переход на PostgreSQL

```bash
npm i pg
export DATABASE_URL=postgres://user:pass@host:5432/quest
npm run migrate
```

`npm run migrate` применяет файлы из `db/migrations` строго по порядку имён,
каждый — в отдельной транзакции, и записывает применённое в `schema_migrations`.
Повторный запуск ничего не делает. Если упала середина файла, он не применяется
целиком — база не остаётся в половинчатом состоянии.

### Однопоточность и гонки

Вместимость слота проверяется **внутри критической секции**, привязанной к слоту:

* в файловом режиме — очередь промисов по ключу слота (разные слоты не блокируют друг друга);
* в PostgreSQL — `pg_advisory_xact_lock` внутри транзакции.

Поэтому два одновременных запроса на последнее место не могут оба пройти.
Проверка вместимости на клиенте — только подсказка, решает сервер.

## 3.1. Развёртывание на Vercel (serverless) — важное ограничение

**Проверено на живом деплое:** файловое хранилище на Vercel брони не сохраняет.
Запись в каталог приложения не переживает перезапуск инстанса, и при этом
`POST /api/bookings` отвечает `201`, а клиент видит экран «вы записаны».
Заявка теряется — площадка о ней не узнаёт.

Поэтому система сама останавливает продажу. Перед созданием брони проверяется
долговечность хранилища, и при отказе API возвращает:

```
503  {"ok":false,"retryable":false,
      "message":"Онлайн-бронирование временно недоступно.
                 Позвоните или напишите нам в WhatsApp — забронируем вручную за минуту."}
```

В журнал пишется `booking_rejected_storage_not_durable` уровнем `error`.
`/api/health` в этом состоянии отдаёт `ok: false`, `storage.writable: false`
и предупреждение с указанием, что именно задать.

**Чтобы бронирование заработало на Vercel:**

1. Создайте базу: Vercel Postgres, Neon или любой managed PostgreSQL.
2. Добавьте `DATABASE_URL` в Environment Variables проекта Vercel.
3. Примените схему: `npm run migrate` (локально, с тем же `DATABASE_URL`).
4. Перезапустите деплой и проверьте:
   `curl -s https://<домен>/api/health` → должно быть
   `database.mode: "connected"`, `storage.mode: "sql"`, `storage.writable: true`.

Драйвер `pg` уже в зависимостях — устанавливать вручную ничего не нужно.
На обычном сервере (VPS, Docker) ограничение не действует: там файловое
хранилище работает, `storage.writable: true`.

## 4. Планировщик

`/api/cron/reminders` — проход напоминаний и истечение броней.

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://example.kz/api/cron/reminders
```

* Требует `CRON_SECRET`. Без него эндпоинт закрыт полностью.
* Рекомендуемый интервал — каждые 15–30 минут.
* Напоминания 24 ч и 2 ч от начала игры; отправка помечается в броне
  (`remindersSent`), поэтому повторный запуск не отправит одно и то же дважды.
* Брони, которые не подтвердили до начала игры, переводятся в статус «истекла».

**Важно:** напоминания уходят только в те каналы, которые настроены
(Telegram / вебхук). Если ничего не настроено, проход фиксирует, кому напомнить,
но никому не пишет и не делает вид, что написал.

## 5. Оплата

Схема по умолчанию — **ручная предоплата**:

1. клиент оставляет заявку, она сохраняется со статусом «ожидает подтверждения»
   и уходит владельцу в Telegram/на вебхук;
2. администратор пишет клиенту в WhatsApp и присылает реквизиты;
3. после оплаты администратор отмечает бронь подтверждённой в своей системе
   учёта — до этого момента слот формально свободен.

Онлайн-эквайринг подключается переменными `PAYMENT_API_URL`, `PAYMENT_API_KEY`,
`PAYMENT_WEBHOOK_SECRET`. Правила, которые соблюдает вебхук
(`POST /api/payments/webhook`):

* подпись тела проверяется (HMAC-SHA256, сравнение за постоянное время); без
  корректной подписи запрос отклоняется;
* редирект клиента на «страницу успеха» доказательством оплаты не считается —
  оплату подтверждает только подписанный серверный вебхук;
* повторная доставка того же платежа не создаёт второго эффекта: событие
  сопоставляется с бронью по номеру платежа;
* в логах нет тела запроса с персональными данными.

## 6. Внешняя система учёта (CRM)

По умолчанию система учёта — собственная база, отдельная CRM не нужна.
Если заведение ведёт учёт вовне, задайте `CRM_API_URL` и `CRM_API_TOKEN`:
бронь выгружается туда после сохранения.

Если выгрузка не удалась, это **не теряется и не скрывается**:

* результат пишется в бронь (`crmSync`), администратор видит пометку
  «CRM: не выгружено»;
* бронь остаётся в статусе «ожидает подтверждения» — то есть система не
  утверждает, что всё согласовано, пока это не подтвердил человек.

## 7. Расписание и занятость

Источник истины по занятости — **реальные брони**. Слот свободен, пока в нём
есть места: площадка работает по фиксированной сетке стартов, все старты
доступны, пока их не заняли.

* `DEMO_AVAILABILITY=1` добавляет **выдуманную** занятость. Это инструмент показа,
  а не функция продукта. На рабочем сайте переменная должна быть снята.
* Внешний календарь подключается через `AVAILABILITY_API_URL`. Если он
  недоступен, API отвечает `503` и честным текстом «расписание недоступно» —
  вместо того чтобы показать устаревшие данные как актуальные.

## 9. Проверки

```bash
npm test              # типы + линтер
npm run verify        # типы + линтер + production-сборка
npm run test:smoke    # сквозной смоук API (нужен запущенный сервер)
```

Смоук-тест требует запущенного сервера с открытым служебным сбросом лимитов:

```bash
# Windows PowerShell
$env:ALLOW_TEST_ENDPOINTS=1; npm start
# в другом окне
npm run test:smoke
```

Тест проверяет доступность слотов, создание брони, цену, защиту от дубля,
валидацию, отказ по прошедшей дате, **переполнение слота**, закрытость
служебных адресов (`/admin` не отдаётся, список броней недоступен анонимно,
планировщик не запускается без секрета), лимит частоты, заголовки безопасности
и наличие структурированных данных.

Скрипт `scripts/scan-hidden-chars.mjs` ищет невидимые символы переноса
(soft hyphen, zero-width space) в исходниках — они незаметно рвут слова
в интерфейсе. Запуск: `node scripts/scan-hidden-chars.mjs`.

## 10. Что сознательно не сделано

Честный список, чтобы не было ложных ожиданий:

* **онлайн-эквайринг не подключён** — есть интерфейс провайдера и проверка
  вебхука, но конкретная платёжная система не выбрана;
* **SMS и e-mail не отправляются** — нужен провайдер; клиент получает
  подтверждение на экране, файл в календарь и ссылку в WhatsApp;
* **внешняя CRM не подключена** — есть адаптер и обработка ошибок выгрузки;
* **e2e-тесты в браузере отсутствуют** — сквозные проверки идут на уровне API
  (смоук-тест); для UI-регрессий нужен Playwright;
* **напоминания клиенту** требуют настроенного канала; без него планировщик
  только фиксирует список.

## 11. Порядок развёртывания

Строго по шагам. 1–4 — подготовка, 5–8 — запуск, 9–10 — приёмка.

1. **Создать базу данных.** Vercel Postgres / Neon / любой managed PostgreSQL.
   Записать строку подключения.
2. **Заполнить переменные окружения** по [`.env.example`](.env.example).
   Обязательные: `NEXT_PUBLIC_SITE_URL` (свой домен, не адрес деплоя),
   `DATABASE_URL`.
   Рекомендуемые: `CRON_SECRET`, `NEXT_PUBLIC_VENUE_TIMEZONE`,
   `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID`.
3. **Установить драйвер и применить схему:**
   ```bash
   npm install
   npm run migrate
   ```
   Миграции идемпотентны и не удаляют данные: повторный запуск ничего не делает.
4. **Проверить готовность до деплоя:**
   ```bash
   npm run verify:production
   ```
   Блокеры (✗) устранить. Предупреждения (⚠) — допустимые режимы, их стоит
   подтвердить с владельцем.
5. **Собрать и запустить:**
   ```bash
   npm run build
   npm start
   ```
6. **Проверить здоровье:** `curl -s <адрес>/api/health`.
   Ожидается `ok: true`, `storage.writable: true`, `database.mode: "connected"`.
7. **Настроить планировщик:** вызов `GET /api/cron/reminders` с заголовком
   `Authorization: Bearer $CRON_SECRET` каждые 15–30 минут (cron хостинга или
   системный планировщик).
8. **Настроить уведомления:** написать боту в Telegram, получить `chat_id`,
   задать `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, перезапустить деплой.
9. **Сделать тестовую бронь:**
   ```bash
   npm run test:booking -- --base=https://<ваш-домен>
   ```
    Проверяет весь путь и печатает номер тестовой брони — удалите её из базы
    и проигнорируйте уведомление в Telegram.
10. **Проверить уведомление:** убедиться, что тестовая заявка пришла в Telegram
    (или на вебхук) с именем, телефоном и номером брони.

### Команды

| Команда | Назначение | Где запускать |
|---|---|---|
| `npm run dev` | разработка | локально |
| `npm test` | типы + линтер | всегда, в том числе в CI |
| `npm run verify` | типы + линтер + сборка | перед деплоем |
| `npm run build` / `npm start` | production-сборка и запуск | сервер |
| `npm run migrate` | применить миграции (идемпотентно) | при деплое |
| `npm run verify:production` | проверка готовности окружения | перед приёмом броней |
| `npm run test:booking` | сквозная проверка бронирования по HTTP | после деплоя |
| `npm run test:smoke` | 46 проверок API (нужен запущенный сервер) | на стенде |
| `npm run seed` | демо-брони для показа. **Только локально**: отказывается работать при `NODE_ENV=production` и на serverless | локально |

## 12. Резервное копирование

Брони — это деньги и расписание площадки. Восстановить их из логов невозможно,
поэтому копии обязательны.

### Что копировать

* таблицу `bookings` (основное);
* `schema_migrations` (чтобы понимать, какая версия схемы у копии).

### Как (PostgreSQL)

```bash
# Полная копия базы в сжатый файл
pg_dump "$DATABASE_URL" --format=custom --file=backup-$(date +%F-%H%M).dump

# Только брони, если база большая
pg_dump "$DATABASE_URL" --table=bookings --format=custom --file=bookings-$(date +%F).dump
```

### Частота и хранение

| Что | Как часто | Сколько хранить |
|---|---|---|
| Автоматическая копия провайдера | ежедневно (включить в панели БД) | 7 дней |
| Своя копия перед изменениями схемы | перед каждым `npm run migrate` | до подтверждения работы |
| Ручная копия перед крупными событиями (праздники, Хэллоуин) | по ситуации | 30 дней |

Managed PostgreSQL (Neon, Vercel Postgres) даёт ежедневные копии и восстановление
на момент времени — для площадки этого достаточно. Дополнительная копия делается
перед миграциями: автоматические копии обычно отстают на сутки, и откатить
неудачную миграцию будет нечем.

### Как восстановить

```bash
# 1. Остановить приём броней, чтобы новые записи не появились во время работы.
# 2. Восстановить копию и переключить DATABASE_URL:
pg_restore --dbname="$DATABASE_URL" --clean --if-exists backup-2026-09-26-0300.dump
# 3. Проверить конфигурацию и связь с базой:
npm run verify:production
# 4. Проверить, что новые заявки снова приходят в Telegram/на вебхук.
# 5. Возобновить приём броней.
```

### Учебная тревога

Раз в квартал восстановить копию в отдельную базу и убедиться, что данные
читаются. Копия, которую ни разу не восстанавливали, — это не копия,
а предположение.

## 13. Откат неудачного деплоя

1. **Определить масштаб.** Открыть `/api/health`: если `ok: true` и
   `storage.writable: true` — приложение работает, проблема локальная.
2. **Откатить код.** На Vercel: Deployments → предыдущий рабочий деплой →
   «Promote to Production». При деплое из репозитория: `git revert <коммит>` и
   новый пуш. Историю в `main` не переписывать: `push --force` ломает работу
   всем, у кого есть копия репозитория.
3. **Не откатывать миграции вслепую.** Миграции аддитивные: новые колонки и
   таблицы не мешают предыдущей версии приложения. Разрушающих операций в
   проекте нет намеренно. Если откат кода всё же требует отката схемы —
   сначала копия, потом ручная правка.
4. **Проверить окружение.** После откатa убедиться, что переменные не были
   изменены вместе с деплоем: `npm run verify:production`.
5. **Посмотреть логи.** События структурированные: искать `booking_failed`,
   `booking_rejected_storage_not_durable`, `payment_webhook_rejected`,
   `rate_limited`.
6. **Проверить деньги.** Сверить брони, созданные за время инцидента: нет ли
   пропущенных заявок, когда клиент видел подтверждение, а записи нет.
   Если такие есть — связаться с клиентами вручную.

## 14. Режимы: демо и продакшен

Смешивать эти режимы нельзя: демонстрация не должна выглядеть как боевая
система, а боевая — тихо работать в демо-режиме.

| | ДЕМО | ПРОДАКШЕН |
|---|---|---|
| Хранилище | файл `.data/bookings.json` | PostgreSQL (`DATABASE_URL`) |
| Расписание | собственные старты площадки; при `DEMO_AVAILABILITY=1` — выдуманная занятость для показа | реальная занятость по броням; внешний календарь при `AVAILABILITY_API_URL` |
| Оплата | ручная предоплата (администратор подтверждает) | онлайн-эквайринг при `PAYMENT_API_*`, иначе так же ручная |
| Уведомления | лог в консоль, если канал не задан | Telegram или вебхук |
| Данные | демо-брони (`npm run seed`), удаляются командой | только настоящие заявки |
| Копии | не нужны | обязательны (см. §12) |
| Мониторинг | не нужен | `/api/health` + логи |

**Признаки демо-режима на рабочем сайте** (их быть не должно): при старте в
логах печатается список проблем конфигурации; `/api/health` отдаёт `ok: false`
или `SCHEDULE — ВКЛЮЧЁН ДЕМО-РЕЖИМ`; в уведомления приходят записи «Тест …»
или «Демо-клиент …».

## 15. Владельцу: с чего начать

**Что это.** Сайт площадки и форма заявки. Сайт показывает квесты, свободное
время и цены, а заявка приходит вам в мессенджер.

**Куда заходить.** Никуда: отдельной панели у сайта нет. Каждая новая заявка
приходит вам в Telegram (или на вебхук) сразу после отправки формы — с именем,
телефоном, квестом, датой и временем.

**Где заявки.** В том же Telegram или в CRM, куда настроены уведомления.
Каждая строка содержит номер брони, квест, дату, время, имя, телефон и
выбранный мессенджер — этого достаточно, чтобы ответить клиенту.

**Деньги.** Оплата по умолчанию ручная: вы присылаете реквизиты в WhatsApp и
подтверждаете получение перевода в своей системе учёта. Онлайн-оплата
подключается отдельно и требует выбора платёжной системы.

**Уведомления.** Чтобы узнавать о заявке сразу, нужен канал: Telegram-бот
(§11 шаг 8) или вебхук. Пока канал не задан, заявки сохраняются, но вы
узнаете о них не сразу — система честно сообщает об этом в `/api/health`.

**Расписание.** Старты квестов заданы в коде (`lib/availability.ts`), их меняет
разработчик. Если расписание ведётся в другой системе, подключается внешний
источник (`AVAILABILITY_API_URL`).

**Как проверить, что всё в порядке.** `npm run verify:production` показывает
одним списком: что готово (✓), что стоит подтвердить (⚠), что мешает работать (✗).

**Как выложить изменения.** Пуш в `main` — при подключённой интеграции Vercel
собирает и публикует автоматически; либо вручную: `vercel --prod`.
