## 2. Что исправлено

**Ложные данные (P0).** Занятость слотов больше не выдумывается. Слот свободен,
пока в нём есть места; единственный источник истины — реальные брони. Демо-профиль
занятости остался, но за явным флагом `DEMO_AVAILABILITY` и никогда не включается
сам. На витрине с честным расписанием слот «17:00 — 3 места» означает ровно то,
что написано.

**Переносы слов (P1).** Причина была не в CSS: буквы анимировались отдельными
`inline-block`-элементами, а у такого элемента есть точка переноса справа — браузер
рвал строку в середине слова. Теперь неразрывным блоком является слово, перенос
возможен только по пробелам. Добавлена страховка в базовые стили (`hyphens: none`,
`word-break: normal`) — на случай, если переносы придут из пользовательских
настроек браузера.

**Календарь и время (P1).** Время игры считается по часовому поясу площадки,
а файл `.ics` собирается из строк даты и времени напрямую, без участия часов
устройства. Гость в любом поясе получает событие на то же самое время.

**Чистота показа (P1).** Тестовые брони вынесены из рабочего файла —
админка открывается пустой и аккуратной.

**Хранилище (P1).** PostgreSQL-репозиторий приведён в соответствие со схемой:
заполняются все объявленные поля, филиал и название квеста берутся из контента,
добавлен снимок расчёта цены и метки напоминаний. Появился детерминированный
раннер миграций с журналом применённого.

**Тесты (P1).** Добавлены `npm test`, `npm run verify`, `npm run test:smoke`,
`npm run migrate`. В смоук-тесте закрыт участок, который проверял не то, что
задумано (детали — в разделе 14).

**Документация (P1).** Появился [`PRODUCTION.md`](PRODUCTION.md) — развёртывание,
переменные, миграции, планировщик, оплата, CRM, подготовка к показу владельцу.
[`.env.example`](.env.example) описывает все переменные, которые читает код.

**Тех. долг (P3).** Удалён BOM из исходников, затронутых ранними правками.

## 3. Наиболее критичные UX-проблемы

1. **Ложная занятость слотов.** Пользователь видел «мест нет» там, где места были,
   и наоборот. Для бизнеса это худший вид ошибки: он либо теряет бронь, либо
   обещает слот, которого нет.
2. **Разорванные слова в заголовках.** Заголовок ломается посередине — первый
   признак небрежного сайта, а именно заголовок читают в первые секунды.
3. **Время игры в календаре гостя.** Бронь есть, а в календаре событие стоит
   на 2–3 часа раньше — человек приходит не тогда.
4. **Тестовые брони в админке.** На показе владелец видит чужие выдуманные
   заявки — подрывает доверие ко всей панели.

## 4. Что взято из анализа лучших escape-room сайтов

**Честно: в этом проходе отраслевое исследование не получено.** Поиск по запросу
о UX бронирования вышел на общие статьи про плагины бронирования и отельные
движки; применимых к escape-room источников с проверяемыми данными не нашлось.
Поэтому ниже — не ссылки на чужие сайты, а перечень паттернов, которые уже
реализованы в проекте и соответствуют общепринятой практике бронирования.
Это инженерная оценка, а не результат цитируемого исследования.

Реализовано и проверено по коду:

* **Sticky CTA** — постоянная кнопка брони на мобильном и на странице квеста;
* **Ближайшие свободные слоты** на главной — до выбора квеста видно, когда можно прийти;
* **Слот как товар** — время и остаток мест в одной строке;
* **Skeleton/loading и disabled-состояния** при загрузке расписания и отправке;
* **Явный экран подтверждения** с номером брони, адресом и файлом календаря;
* **Поделиться с друзьями** — отдельная кнопка, формирующая готовый текст;
* **День рождения и большая компания** — отдельные точки входа, не отдельный каталог;
* **Прозрачная цена** — состав чека показывается до подтверждения;
* **Ответы до брони** — FAQ и блок «перед входом» снимают возражения.

## 5. Что нового добавлено

* Провайдеры с честным отказом: расписание, оплата, CRM, канал уведомлений.
  Неподключённая подсистема **не притворяется работающей**.
* Атомарная проверка вместимости внутри критической секции слота (файловый режим —
  очередь по слоту, PostgreSQL — `pg_advisory_xact_lock`).
* Ключ идемпотентности на заявке: повторная отправка не создаёт вторую бронь.
* `/api/health` для мониторинга — без секретов в ответе.
* `/api/cron/reminders` — напоминания и истечение неподтверждённых броней,
  с защитой от повторной отправки одного напоминания.
* Восстановление номера брони после обновления страницы — на устройстве
  хранится только неперсональная часть (номера, даты, суммы; без имени и телефона).
* События воронки без персональных данных.

## 12. Security

Проверено смоук-тестом против production-сборки:

| Проверка | Результат |
|---|---|
| Список броней без входа | 401 |
| Вход в админку с чужого домена | 403 |
| Смена статуса без сессии | закрыта |
| Лимит частоты | 429 после порога |
| CSP, X-Frame-Options, Permissions-Policy, nosniff | установлены |
| `X-Powered-By` | скрыт |
| Ответы API | `no-store` |

Дополнительно по коду: пароль администратора и секрет сессии обязательны, дефолтных
паролей нет; вебхук оплаты проверяет подпись сравнением за постоянное время;
сброс лимитов открывается только явной тестовой переменной.

Остаточный риск: лимит частоты считается в памяти процесса — на нескольких
инстансах счётчики независимы, нужен общий стор (Redis).

## 14. Tests

Итог последнего прогона на чистом состоянии данных:

```
npm test              → PASS (tsc --noEmit + eslint)
npm run build         → PASS
npm run test:smoke    → 46 пройдено, 0 провалено
```

**Отдельно про один найденный сбой.** Первый прогон дал 43 из 44 проверок:
упала проверка переполнения слота — «сервер продал больше мест, чем есть».
Разбор показал, что это утверждение теста, а не поведение системы:

* прямой эксперимент по HTTP: слот на 15 мест заполняется полностью, повторная
  заявка получает **422** с текстом «Этот слот только что заняли…» — то есть
  вместимость сервером проверяется;
* причина ложного срабатывания — накопленные тестовые брони в `.data` (к тому
  моменту их было 100) меняли состояние между шагами, а тест не проверял
  промежуточный результат.

Что сделано: в тест добавлено утверждение «после заполнения слот закрыт», которое
разделяет две разные проблемы («слот не закрылся» и «сервер продал лишнее»).
Это устраняет класс ложных тревог, при которых исправный код выглядит сломанным.
Точную первопричину исходного сбоя воспроизвести не удалось (состояние данных
изменилось), поэтому она **не заявлена** как найденная — заявлено только то,
что проверено: промежуточное состояние и отказ сервера.

Дополнительно: `scripts/scan-hidden-chars.mjs` ищет невидимые символы переноса
в исходниках.

**Не сделано:** браузерные e2e-тесты (Playwright отсутствует — нет зависимости;
набор сценариев и обоснование приведены в разделе 15).

## 15. Remaining risks

1. **Нет браузерных e2e-тестов.** Смоук покрывает API и разметку, но не UI-сценарии.
   Это главный незакрытый пункт из требований (нужны Playwright и установка браузеров).
2. **Реальный проход в браузере не выполнялся.** Консоль и сеть на живых устройствах
   не проверялись; заявленное «0 ошибок в консоли» не подтверждено.
3. **Лимит частоты в памяти процесса.** Не масштабируется на несколько инстансов.
4. **Файловое хранилище не предназначено для нескольких инстансов.** Для продакшена
   нужен `DATABASE_URL`; на одном сервере файла достаточно.
5. **Онлайн-оплата не подключена** — интерфейс и проверка вебхука есть, провайдер
   не выбран. Сейчас работает ручная предоплата.
6. **SMS и e-mail не отправляются** — нет провайдера; клиент получает подтверждение
   на экране, файл календаря и ссылку в WhatsApp.
7. **Внешняя CRM не подключена** — есть адаптер, таймауты и фиксация ошибок выгрузки.
8. **Демо-профиль занятости** должен быть снят на рабочем сайте: он показывает
   выдуманную загрузку.
9. **Юридические тексты** (политика обработки персональных данных) собираются
   под город и требуют проверки юристом.

## 16. Production readiness

**Готово к запуску на одном сервере:** бронирование, проверка вместимости на
сервере, защита от дублей, цена из единого источника, админка, доступность слотов,
SEO-разметка, заголовки безопасности, лимит частоты, health-check, миграции,
документация по эксплуатации.

**Требует решения перед публичным запуском:**
`ADMIN_PASSWORD` и `ADMIN_SESSION_SECRET` (без них админка отключена),
`NEXT_PUBLIC_SITE_URL`, `CRON_SECRET` и внешний вызов планировщика,
канал уведомлений (Telegram или вебхук) — иначе владелец узнаёт о бронях
только из админки.

**Требует доработки для масштабирования:** общее хранилище счётчиков частоты
и переход на PostgreSQL.
